# What has been checked against Monty

A port that looks right is worth nothing. The only claim worth making is that
specific numbers agree with Monty's, and the only way to know is to have Monty
produce them.

This file lists every such check: what was compared, against what, how closely it
agreed, and where the test lives. Anything not listed here is written from a
reading of Monty's source — plausible, tested for its own behaviour, but not
confirmed to be Monty's arithmetic.

Three kinds of check, strongest first:

1. **Replayed** — Monty's own code ran in this environment and its answers were
   written to a committed fixture; a test feeds the port the same input and
   compares. This is the only kind that says "the same numbers".
2. **Recorded** — Monty ran a whole episode; the percepts and conclusions were
   written down; the port is fed the percepts and must reach the conclusion.
3. **Counted** — the configuration and the naming agree, so the same experiment
   is described the same way on both sides. Numbers are not involved.

Fixtures are generated by the scripts in `scripts/`, never hand-edited. Each
generator runs Monty's own code out of the `../monty-orig` checkout, so the
revision it recorded is whatever that checkout is at. The parity tests are the
only place a tolerance is allowed to be loose, and each says why it is.

### The arithmetic this pins, by class

Each of the following was either measured before it was ported or measured after
and corrected — which is the point of measuring rather than recalling:

- Half-life decays: `tau_t`/`tau_s` are the times and distances at which a weight
  *halves*, so the exponent divides by `tau / ln 2`.
- OpenCV's `INTER_CUBIC`: `A = -0.75`, the half-pixel coordinate
  convention `(i + 0.5) * scale - 0.5`, and clamping at the border.
- OpenCV's `getGaborKernel` modulates with `cos(2πx_r/λ − ψ)` — a
  *minus* psi. A plus psi agrees at `ψ = 0` and is wrong everywhere else; that is
  exactly how a first reading of the C++ goes wrong. Verified over 100 kernels to
  `3e-8` before the port was written.
- `cv2.filter2D` is correlation (no kernel flip) with
  `BORDER_REFLECT_101`; measured to `4e-6` on random images.
- `GaussianBlurRGB`'s kernel is what `cv2.GaussianBlur` answers for the same
  sigma, to `1e-7` (`test/monty/frameworks/environment_utils/transforms/image_transforms_test.exs`).

The evidence figure is worth reading carefully: a slope is a difference of two
nearly equal numbers, so the last digits of the evidence decide which hypotheses
survive. Agreement to a thousandth in evidence is what keeps the *count* of
hypotheses within a couple — it is not slack in the arithmetic, it is the
arithmetic amplifying float32 from the export.

## Run: the prologue a studio run now has

An episode no longer begins wherever the stand-in world left the agent. It begins
where Monty's own positioning procedures put it: `Monty.Runtime.Positioning`
replays `ExperimentEnvironment.pre_episode` — a fresh look, the procedure's
actions, another look, until the procedure is finished — and only the last
procedure's verdict decides whether the episode may start.

What that means for a studio run of `base_config_10distinctobj_dist_agent`: both
procedures from the config run (`view_finder`, which may walk towards the object,
then `patch`, which may only turn), the world takes **25 steps** to position, and
the run then starts from the pose they chose. The *procedure's* decisions are
compared with Monty's in the table above; the loop itself is Monty's protocol
replayed, not a recorded comparison, because it depends on a world.

Both the prologue and the episode go through `Monty.Experiment.Environment.Interface`
— Monty's own layer — so "step the world and transform what came back" is
defined once. A step of a run is `Interface.step/2`, and the positioning
procedures' actions step the same interface.

Which object the episode is about, and which semantic id the world stamps on it,
used to be a guess written into `Monty.Studio.Setup` ("the target is 1", "no
distractors"). Both are `OneObjectPerEpisodeInterface`'s answers — the id from
`semantic_label_to_id`, the count from the config's `num_distractors` — and are
now asked of it (see §2.16 for what the stand-in world still decides).

An episode also ends the way Monty's does: `Monty.Runtime.Episode` and the
studio's run both ask a recognition policy each step instead of counting to a
budget, and apply the two reactions a policy can ask for (`start_exploring`,
`time_out_lms`). The default is `AnyPolicy([MontyIsDone, MaxTotalSteps])` —
Monty's own default unioned with the ceiling, which is what `:max_steps` means —
and the studio builds the policy its config names, falling back to `MontyIsDone`
where a config names none, which is Monty's fallback too.

A run also starts with Monty's own pretrained memory when its config names a
model this machine has exported: `priv/monty/libraries/<model>.jsonl.gz`, loaded
by `Monty.Studio.Memory` into the learning module the config describes
(`priv/monty/libraries/README.md` records where the library came from and the
command that produced it). A config that names a model with no library is not an
error: the run starts empty and says so as a warning before it takes a step,
because a run with nothing to recognise with cannot recognise anything, however
long it runs. Loading is six seconds of gunzip and graph building, so the decoded
memory is kept per library and each run is handed a copy — learning writes to it,
and two runs must not share one (§2.18 of `monty-bugs.md`).

What a run reports therefore changed: it says what its learning modules
concluded, or that they were timed out. `tutorial/first_experiment` now ends
after **one** step, and that is the config's own rule — its termination group is
`MinEvalMaxTotalSteps` over `StepLimit(max_eval_steps: 1)` — with the module
timed out rather than left blank, because the studio runs no training epochs and
the memory is empty. A configuration whose learning module is a stand-in (the
base config, whose `EvidenceGraphLM` needs a pretrained model this port cannot
load yet) runs its whole session budget and reports no conclusion, which is what
a stand-in is.

## What is **not** verified

Saying this plainly matters more than the table above:

- **The world.** A studio run happens in a synthetic stand-in world, and its
  numbers are that world's numbers. A config's *own* model can also be run
  against Monty's own world — `scripts/probe_world_episodes.exs`, below — and
  there every episode so far ends on the object Monty names, in a number of
  steps that is Monty's only up to the random-stream difference below.
- **The path of a run, past its first steps.** The model's draws are Monty's now
  (§2.1 of `monty-bugs.md`), and the first action of an episode is Monty's to the
  last digit — but from some later step the two runs part, and two of ten episodes
  of the comparison above agree on their step count. Two draw sites are still on
  their own stream (`DepthTo3DLocations` noise and a camera's message noise), and
  neither is in the config compared here, so that is not yet the explanation.
- **The simulator peer in CI.** Habitat and MuJoCo need Monty's pinned conda
  environment, so the peer that drives Monty's own environments runs here as a
  probe and not as a test: no CI job has that interpreter.
- **The default policy's arithmetic.** `DistantPolicySelector` is verified for
  *routing* — which goal reaches which policy, and what `LookAtGoal` answers —
  but the fallback it hands the step to is `InformedPolicy`, which needs a
  percept full of hypotheses, and Monty's hypotheses come from learning modules
  that import `torch`. So the recording records the routing and nothing of the
  fallback's own numbers; those are tested where they live, without Monty.
- **An episode, end to end — and the first honest measurement of one.** Ten
  episodes of `base_config_10distinctobj_dist_agent` are recorded
  (`test/fixtures/monty_dist_agent_10episodes.jsonl`: 43, 27, 28, 27, 36, 28, 40,
  43, 35 and 31 steps, all `match`, on the ten YCB objects), and two probes
  replay them through the port's own composition — the config's learning module
  with the library in `priv/monty/libraries/`, the config's recognition policy,
  the real step coordinator — with the recording standing in for the world.

  What they measure, so far: the learning module the config builds reproduces
  Monty's evidence to the printed digit on every step (step 0 `mug=0.879
  bowl=0.822 mustard_bottle=0.806` on both sides; step 4 differs in the third
  decimal, which is float ordering), **both on its own and through the
  coordinator's routing** — `scripts/probe_dist_agent_evidence.exs` and
  `scripts/probe_dist_agent_routing.exs` — and it holds the same hypothesis space:
  the number of hypotheses per object matches Monty's at every step (888, 1776,
  2664, … for the mug; `scripts/probe_episode_conclusion.exs`).

  **Nine of the ten episodes now replay to Monty's conclusion, on Monty's own
  step** (`scripts/probe_dist_agent_episodes.exs`): mug 43, bowl 27,
  potted_meat_can 28, spoon 27, strawberry 36, mustard_bottle 28, golf_ball 43,
  c_lego_duplo 35 and banana 31 — every one of them the object Monty recognised
  and the step it recognised it on. The dice is the exception: Monty concluded
  on step 40, its last, and the port's symmetry count reset there instead of
  reaching five, so the episode ran out of recorded steps.

  Getting there found two bugs, one in the port and one in the recorder:

  * A run was never told the experiment's `monty_args`, so `min_eval_steps` was
    0 and the terminal condition was asked on the *first* step. Monty does not
    ask until an evaluation has taken 20 matching steps (`MontyBase.min_steps`),
    and the mug episode ended on step 8 until that number was passed through
    (`Setup.model_spec/2`).
  * `record_monty_episode.py` kept its per-module cursor into the module's
    buffered percepts across episodes, while the buffer itself is reset at each
    episode start — so every episode after the first lost its *first* percept in
    the recording. A replay fed nine of ten episodes one observation short,
    starting from the wrong view. With the cursor reset, eight of the nine
    remaining disagreements disappeared.

  The numbers the terminal condition turns on are now recorded too —
  `record_monty_episode.py` wraps Monty's `_check_for_unique_poses` to keep the
  symmetry count, the pose-count, the two maxima it compares and, when they are
  few enough, the pose ids — and `scripts/probe_episode_conclusion.exs` prints
  both sides of them step by step. That is how the dice was placed, and the
  numbers are exact (`scripts/probe_pose_sets.exs`): on its last step both sides
  keep the same 24 poses out of their previous step's, but the port holds 28 in
  total and Monty 26 — so the 90%-overlap rule reads 24/28 = 0.86 for the port
  and 24/26 = 0.92 for Monty, and where Monty's symmetry count reaches five the
  port's starts again. The two extra poses are ones whose evidence sits inside
  20% of the best here and outside it there, and the two implementations'
  evidence agrees only to about `2e-4` relative (`29.44` against `29.46`): a
  boundary case, not a different rule — and the boundary is the *memory's*,
  not the arithmetic's: on every step of that episode both sides pick the same
  hypothesis id, and its rotation is `2.7e-7` rad apart
  (`scripts/probe_pose_drift.exs`), which is the six-decimal rounding the export
  writes node positions and features with. A hypothesis whose feature sits within
  that of its tolerance is scored differently in the two, and its evidence then
  runs a fraction apart for the rest of the episode. Matching Monty's arithmetic
  to the last bit would mean importing its pickles without rounding them.

  The claim itself is a test now: "an episode of Monty's ten-episode evaluation
  ends on the object Monty named, after the steps Monty took"
  (`test/monty/recording_episode_test.exs`) replays the bowl — the shortest of
  the nine that agree — through the config's own composition with the recorded
  release's memory, and takes 27 steps to the bowl. It fails if a run is not
  given the experiment's `min_eval_steps` (21 steps instead of 27).

  An episode costs tens of seconds, not milliseconds: a step is 0.8–1.9 s at this
  memory size, and that is the learning module's own matching, not the runtime —
  a step that reads the model's four policy fields used to copy the 43 MB of
  pretrained graphs out of the coordinator to answer with them (0.24 s a step,
  and 43 MB of garbage), and that is now a four-field reply costing 4–9 µs
  (`scripts/probe_state_cost.exs`). So the ten-episode sweep stays a probe until a
  step gets cheaper.
- **The environment the recordings came from.** `frameworks/models/object_model.py`
  pulls in `torch` and `torch_geometric`, so a recorded Monty episode needs a
  second interpreter. This machine has Monty's **own pinned one**: the conda
  environment `tbp.monty` (Python 3.8.20, `torch` 1.13.1, `torch_geometric`
  2.1.0, `numpy` 1.23.5, `habitat_sim` 0.2.2) matching `environment_arm64.yml`,
  with YCB object meshes under `$MONTY_DATA` and pretrained models under
  `$MONTY_MODELS`. Recordings must name their `PYTHONPATH` entries absolutely,
  or they import a different Monty checkout.
  `scripts/setup_monty_oracle.sh`
  builds a pip-only stand-in where Monty's environment is absent, with newer
  versions (§2.15 of `monty-bugs.md`).
- **Distractors.** `OneObjectPerEpisodeInterface` computes which objects a
  distractor may be drawn from and refuses to place any (§2.16), because the
  stand-in world holds one object. A config that asks for distractors therefore
  errors rather than running an evaluation that would silently be about a lone
  object.
- **`TwoDSensorModule`**, which needs a dataset that is not present.
- Known, documented differences that are *not* agreement: `rgb_to_lab` to
  `2.67/255` (§1.12), OpenCV's mixed-axis `INTER_AREA` (§1.13), and
  a pixel with no depth becoming the nearest patch (§1.14).

## Monty's own world, behind the port

The world a run needs is Python — `HabitatEnvironment` and the experiment's own
environment interface — and `Monty.Simulators.Port` is the boundary to it:
length-prefixed JSON over a pipe, one request at a time.
`scripts/monty_simulator_peer.py` is the other side, running **Monty's own**
environment: it composes the experiment's config, builds the environment and the
eval interface exactly as `MontyExperiment.load_environment_interfaces` does, and
starts each episode the way Monty's epoch loop does — `pre_epoch` once, then
`post_episode` and `pre_episode` per episode, including the interface's own
positioning procedure and its rng, reseeded per episode from `episode_seed` as
`MontyExperiment.pre_episode` does. It logs each episode's seed and target to
stderr, out of the pipe's way, so a run can be told which episode it is in.

What comes back is decoded on this side: `Protocol.proprioceptive_state/1` turns
Monty's maps into the port's `AgentState`/`SensorState` (`wxyz` quaternion to a
`Monty.Geometry.Rotation`), so the motor system can act on them, and an action
travels the other way because `ActionJSONEncoder` carries a
`{w, x, y, z}` as the four numbers Monty's `dict(action)` has.

Measured on this machine — `base_config_10distinctobj_dist_agent`, its own
`surf_agent_1lm_10distinctobj` memory, a Habitat scene built in about half a
minute, `scripts/probe_world_episodes.exs`:

| 2 | bowl | 28 | 27 |

## The stream: Monty's numbers, and where the paths still part

The random stream is Monty's now. `Monty.Random.Numpy` is MT19937 seeded as NumPy
seeds it, `random_sample` and `normal` as NumPy computes them — including the
spare draw `normal` keeps in its state — and it is held to NumPy's own numbers
for three seeds rather than to its statistics. `Monty.Random.Stream` is the one
stream an episode draws from: a process per model, reseeded when the episode's
seed changes, drawn by whatever is stepped next. The salience module's dither and
the goal generator's coin flip — the two things that draw in this config — take
their numbers from it, in Monty's order, because the coordinator now steps its
sensor modules one at a time instead of in a barrier: a barrier would decide which
module drew first by which call arrived first.

The first action says the stream is right. Monty asks the world for
`turn_left 16.782644145270698°` + `look_up 20.802956601860625°`; so does the port,
to the last digit (`scripts/probe_world_episodes.exs` writes the port's actions,
`scripts/record_monty_episode.py` records Monty's). Before the stream it asked for
`turn_left -33.06°` + `look_up 11.29°`, and the episode it walked was a different
one.

Episodes 1 and 3 then agree with Monty step for step, and the rest do not, so the
stream was necessary and is not sufficient. Both sides now log where the stream
stands after each step (`get_state()[2]` on Monty's side,
`Monty.Random.Stream.state/1` on ours), and for the first episode the two rows
are:

| step | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Monty, words drawn | 228 | 40 | 400 | 420 | 512 | 456 | 6 | 264 |
| the port | 228 | 40 | 400 | 420 | 512 | 456 | 6 | 92 |

The same words are consumed, step for step, for seven steps. And the first action
that differs between the two runs is chosen while that is still true — at the end
of step 6 both streams stand at word 184 — so **the remaining difference is not
the random stream**. The two runs hold the same numbers and make different
decisions out of them: they part at the first step where the model has a goal to
pursue, which is where the learning module's evidence starts driving the motor
system rather than the salience module's dither. From step 8 the draws differ too,
but that is downstream: a different decision is a different view, and a different
view is a different number of pixels to score.

Both runs also log what the module believed after each step, and that says where
the two part. Through steps 3, 4 and 5 the most likely hypothesis is the *same
hypothesis*: the same location and the same rotation, in Monty's `wxyz` order and
to the last digit (`[0.685139, −0.016442, 0.728086, −0.014276]` as `xyzw` on both
sides once the orders are compared like for like). What differs is the evidence:
`4.026` against Monty's `4.046`, `5.577` against `5.626`, `7.035` against
`7.176` — a fifth of a percent, then one, then two. And what that moves is the
objects a run keeps: at step 3 Monty drops `bowl` because its best evidence,
`3.2336`, sits `0.1 %` under the 20 %-of-best cutoff, and the port keeps it. By
step 6 a near-tie inside `mug` has broken the other way and the two runs track
poses that are mirror images, which is the jump that differs.

The percepts are not the explanation. Diffing the feature map the module scored
against Monty's, for the same step and the same observation, they agree to the
last digit in every feature — `hsv`, `principal_curvatures_log`, `object_coverage`,
`on_object`, `pose_fully_defined` — *except* `pose_vectors`, where the port's two
principal curvature directions are the **negatives** of Monty's. That sign is
arbitrary in Monty's own computation (`principal_curvatures` returns whatever
eigenvector `numpy.linalg.eig` gives and fixes only `dir2`, by the right-hand rule
about the normal) — and Monty's own evidence says the sign cannot matter:

```python
# Since curvature directions could be rotated 180 degrees we define
# the error to be largest when the angle is pi/2 (90 deg) and angles 0 and
# pi are equal.
cd1_error = np.pi / 2 - np.abs(cd1_angle - np.pi / 2)
```

so a flipped direction scores the same. The sign is decorative; it is not what
moves the evidence by a fifth of a percent, and the search for that is in the
module's own arithmetic, not in the percept: the same hypothesis, on the same
percepts, carries `4.026` where Monty's carries `4.046`. The recorder already
writes the per-graph evidence Monty accumulated per step (`hypotheses`,
`max_evidence`, `within_x_percent`, `top_evidence`), so that is the next thing to
hold the port's numbers against.

Two rules, learned the hard way:

- Run the recorders with an interpreter that has what they import. Those needing
  OpenCV must use a Python 3.13 environment; the others are happy with the
  repo's default. `scripts/setup_monty_oracle.sh` builds the one the full-Monty
  recorders need where Monty's pinned conda environment is absent
  (`VENV=.monty-oracle WITH_TORCH=1 ./scripts/setup_monty_oracle.sh`), and prints
  the versions it installed, because they are newer than Monty's (§2.15 of
  `monty-bugs.md`).
- Never tighten a tolerance to make a fixture pass, and never loosen one without
  saying in the test *why* the difference is not the port's. A too-generous
  tolerance hides a port bug; a too-tight one hides float32.
